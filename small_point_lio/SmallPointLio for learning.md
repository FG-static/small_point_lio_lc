# SmallPointLio 学习记录

## 数据融合整体理解

`small_point_lio` 的核心流程可以理解为：IMU 数据和点云点数据在处理逻辑上是分开的，但它们最终都会更新同一个 ESKF 状态。系统先把 IMU 和点云分别放入队列，然后在 `handle_once()` 中根据时间戳顺序处理，谁的时间戳更早就先处理谁。

如果 IMU 数据更早，系统会先将状态推进到该 IMU 时间戳，然后调用 `h_imu()` 构造 IMU 观测残差。IMU 观测主要约束状态中的角速度、加速度以及陀螺仪/加速度计零偏。随后 `update_imu()` 将这些观测残差丢进 ESKF 进行状态更新，同时 `predict_cov()` 会推进协方差。

如果点云点更早，系统会先将状态推进到该点的时间戳，然后调用 `h_point()`。在已经存在历史点云地图的情况下，`h_point()` 会把当前点变换到 odom/map 坐标系，在 iVox 子地图中寻找最近邻点，用这些历史点拟合局部平面，再计算当前点到该平面的点面距离残差。这个过程类似点面 ICP 的几何误差模型，但不是先求出一个独立的 ICP 位姿变换，而是直接把点面残差和雅可比矩阵作为观测送入 ESKF 更新。

因此，更准确地说：

```text
IMU 提供运动状态约束；
LiDAR 点云通过历史地图提供点面几何约束；
二者按时间戳交错更新同一个 ESKF 状态。
```

## 点云畸变处理理解

这个项目没有单独的 `deskew()` 或 `undistort()` 函数，也没有先生成一整帧去畸变点云再做配准。它的方式是点级处理：每个点都有自己的时间戳，系统在处理某个点之前，会调用 `predict_state(point_timestamp)` 将当前 ESKF 状态推进到这个点的采样时刻，然后再做 `h_point()`。

状态推进使用的是当前滤波器状态中的速度、角速度、加速度和重力：

```text
p <- p + v * dt
R <- R * Exp(ω * dt)
v <- v + (R * a + g) * dt
```

这些状态量本身又会被 IMU update 持续修正。因此它不是简单地把整帧点云都当成同一时刻，而是让每个点在自己的时间戳上参与更新，从而实现一种隐式的点级运动补偿。

## 队列与并发问题

基本上不会出现 IMU 和 point 同时抢占读写 ESKF 状态的问题。当前 ROS 2 节点没有显式使用多线程 callback group，也没有加锁；正常情况下默认 callback group 是互斥执行的，因此 LiDAR callback 和 IMU callback 不会同时进入 `handle_once()` 修改同一个状态。

算法内部使用三个队列：

```text
imu_deque：IMU 数据
point_deque：过滤/降采样后的点，用于 ESKF 点面更新
dense_point_deque：较密点云，用于发布注册点云
```

`handle_once()` 会要求三个队列都有数据，然后比较队头时间戳，处理最早的数据。这样做是为了避免在缺少某类数据时提前处理可能顺序错误的数据。

如果某个队列里有很旧的数据，它仍然会先参与时间戳比较。如果该数据的时间戳已经旧到小于滤波器当前时间 `time_current`，代码会直接 `pop_front()` 丢弃；如果它只是相对真实系统时间很旧，但仍然晚于 `time_current`，则会被当作积压数据继续处理。这种情况不会造成时间顺序错误，但会带来实时性延迟。

## 关于学长提出的 IESKF 想法

学长的想法可以理解为：

```text
先用当前 ESKF 点级处理结果得到去畸变/注册后的点云；
再拿这批点云与历史地图做一次整帧 IESKF scan-to-map 更新。
```

当前项目已经实现的是逐点 ESKF scan-to-map：每个点都会和历史 iVox 地图构造点面残差并更新状态。它没有实现整帧 IESKF 二次更新。

如果后续要加入 IESKF，需要注意同一批点云观测可能被重复使用：当前逐点 `update_point()` 已经用这些点更新过状态，如果整帧 IESKF 再用同一批点云更新一次，就可能导致信息重复计入，协方差过度收缩。比较合理的方向是明确 IESKF 的角色：它是作为当前 ESKF 结果的 scan-to-map refinement，还是要替代逐点点云更新成为主要 LiDAR 更新方式。
